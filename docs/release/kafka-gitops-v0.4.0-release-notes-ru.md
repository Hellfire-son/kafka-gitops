# Kafka GitOps v0.4.0

Kafka GitOps управляет топиками, конфигурацией и ACL Apache Kafka на основе
описания желаемого состояния, хранящегося в системе контроля версий. В версии
0.4.0 обновлены Java и зависимости, улучшена диагностика plan/apply, добавлены
увеличение числа разделов и управление коэффициентом репликации с повторными
проверками безопасности и учётом ELR.

## О проекте

Это независимый форк, сопровождаемый сообществом в репозитории
[Hellfire-son/kafka-gitops](https://github.com/Hellfire-son/kafka-gitops). Его
основа — [joschi/kafka-gitops 0.3.1](https://github.com/joschi/kafka-gitops).
Оригинальный проект —
[devshawn/kafka-gitops](https://github.com/devshawn/kafka-gitops), автор —
**Shawn Seymour**. Исходные уведомления об авторских правах и имена пакетов
`com.devshawn.*` сохранены.

Проект распространяется по
[Apache License 2.0](https://github.com/Hellfire-son/kafka-gitops/blob/main/LICENSE).
Включённые сторонние компоненты сохраняют собственные лицензии и уведомления.
Форк не имеет официального одобрения или поддержки Apache Software Foundation,
Arenadata, Confluent либо первоначальных сопровождающих проекта.

## Что нового

Изменения относительно исходной версии 0.3.1:

- **Среда выполнения и сборка:** Java 21, Kafka Client 4.4.0, Gradle Wrapper
  9.9.1 и Shadow 9.6.1. Один универсальный JAR используется с проверенными
  версиями Kafka 3.x и 4.x.
- **Зависимости:** Jackson Core/Databind/YAML 3.3.0 с Annotations 2.23,
  Logback 1.6.6, SLF4J 2.0.20, Picocli 4.7.7, SnakeYAML Engine 3.2,
  LZ4 Java 1.14.0, Snappy Java 1.1.10.12 и Zstd JNI 1.5.7-26.
- **Конфигурация:** `--command-config` принимает стандартный файл свойств клиента
  Kafka. Явно заданные значения файла имеют приоритет над соответствующими
  переменными окружения; окружение может заполнять отсутствующие свойства.
  Переменные Kafka необязательны. Адреса bootstrap необходимо задать явно.
- **Диагностика:** ограничено время ожидания соединения и метаданных, введены
  стабильные категории ошибок и отдельные этапы загрузки конфигурации,
  подключения, чтения метаданных и планирования. Чувствительные параметры, в том
  числе старые и новые значения конфигурации топиков, маскируются.
- **Читаемый план:** показаны фактические и желаемые значения числа разделов и
  RF, старые и новые настройки, упорядоченные назначения реплик, сведения о
  брокерах и стойках, предупреждения и причины блокировки. Текстовая диагностика
  отделена от исполняемого JSON. Заблокированный план не экспортируется;
  существующий выходной файл остаётся без изменений.
- **Операции с топиками:** создание, изменение конфигурации, увеличение числа
  разделов, детерминированное увеличение и уменьшение RF. Уменьшение числа
  разделов не поддерживается. Существующие профили ACL и явно включаемая
  семантика DESCRIBE сохранены; автоматическая выдача DESCRIBE не добавлена.
- **ELR и старые брокеры:** проверка возможностей различает неподдерживаемые или
  неизвестные метаданные и доказанную неприменимость функции. При включённом ELR
  выполнение допускается с подтверждённо пустыми ELR/LastKnownELR и здоровым ISR.
- **Применение:** разрешения и метаданные заново проверяются перед записью RF,
  проверки повторяются между пакетами, выполнение переназначения контролируется
  в пределах заданного времени, а завершение подтверждается независимо.
  Подтверждение приёма запроса само по себе не означает успех.

## Управление коэффициентом репликации

Расхождения RF учитываются в `plan` по умолчанию. `--no-manage-replication`
исключает изменения RF; при `apply` этот флаг отклоняет сохранённый план с любой
операцией RF до всех записей. `--manage-replication` сохранён как устаревший
совместимый псевдоним. Противоположные флаги RF конфликтуют.

**Увеличение:** детерминированный алгоритм выбирает проверенные допустимые
брокеры, сохраняя контекст упорядоченных назначений. Политика по умолчанию
`plan --replication-rack-policy RACK_AWARE` требует полных сведений о стойках и
проверяет распределение реплик между ними. `BROKER_ONLY` выбирается явно и
означает принятие риска отсутствия защиты на уровне стоек; остальные проверки
безопасности сохраняются.

**Уменьшение:** `plan` показывает уменьшения без отдельного разрешения. Для
выполнения необходимо заново указать `apply --allow-replication-decrease`;
совместимый параметр у команды `plan` такого разрешения не предоставляет.
Глобальный `--no-delete` запрещает уменьшение RF даже при наличии
`--allow-replication-decrease`. Целевое назначение должно сохранять текущего
лидера, использовать реплики из исходного ISR, соответствовать политике стоек
и иметь RF не ниже действующего `min.insync.replicas`. GitOps не уменьшает
`min.insync.replicas` автоматически.

Повторно проверяются ID кластера, UUID топика, число и номера разделов, прежние
упорядоченные назначения, топология брокеров и стоек, доступность, исключение
брокеров из работы, запрет использования каталогов, здоровье каталогов журналов,
действующие настройки, сведения о функциях, свежесть снимка и конкурирующие
переназначения. Сохранённый JSON не заменяет актуальные метаданные и разрешение
на запись. Изменение идентификаторов, топологии, конфигурации или назначений
может сделать план неактуальным и потребовать нового планирования.
Несовместимые одновременные изменения разделов или конфигурации отклоняются.

ISR должен быть здоровым, а лидер — допустимым. Наличие реплики в ELR не
доказывает её текущую синхронизацию. При включённом ELR поддерживаемого уровня 1
наборы ELR и LastKnownELR должны быть известны и пусты. Непустые или некорректные
наборы блокируют операции RF. Отсутствующие поля остаются `UNKNOWN` и не
подменяются пустыми списками. На старых Kafka выполнение возможно при отдельном
положительном доказательстве ELR `NOT_APPLICABLE`; одного отсутствия поля или
функции недостаточно.

Критические сведения со значением `UNKNOWN`, опасное состояние ISR/ELR,
недостаток допустимых брокеров или стоек, неактуальные идентификаторы или
назначения, конкурирующее переназначение, недопустимое соотношение RF/minISR
либо отсутствие разрешения приводят к `BLOCKED`. Некоторые некритические
неопределённости общей политики размещения или запаса диска могут оставаться
предупреждениями; это не доказывает достаточность ресурсов и не отменяет
обязательных проверок. Успешный предварительный план всё равно требует
`FRESH_PREFLIGHT_REQUIRED` при применении.

Исполнитель различает приём запроса/`ACCEPTED`, выполнение `RUNNING` и завершение
`COMPLETED`. Для завершения необходимы точное совпадение упорядоченных целевых
назначений, полный целевой ISR, допустимый лидер, сохранение идентификаторов и
условий безопасности, отсутствие активного переназначения. Независимая конечная
проверка может дождаться согласования кешей метаданных в пределах отведённого
времени. Отсутствие конечного подтверждения означает ошибку/`UNKNOWN`, а не
успех. Автоматический откат, отмена и подмена целевых назначений не выполняются.

**`plan` никогда не изменяет Kafka. Изменения выполняются только явным `apply`.**

## Совместимость

Исторические интеграционные испытания и приёмка окончательного релизного JAR —
разные наборы подтверждений. Окончательный JAR определяется SHA-256, указанным ниже.

| Целевая система | Предыдущие интеграционные испытания | Приёмка окончательного JAR v0.4.0, 2026-11-14 |
|---|---|---|
| Apache Kafka 3.2.3 | PASS: топики, конфигурация, увеличение числа разделов, RF 1 → 2 → 3 → 2 | PASS: plan, новый тестовый топик, RF 1 → 2 |
| Apache Kafka 3.7.1 | PASS: топики, конфигурация, увеличение числа разделов, RF 1 → 2 → 3 → 2 | PASS: plan, новый тестовый топик, RF 1 → 2 |
| Apache Kafka 4.4.0 | PASS: топики, конфигурация, увеличение числа разделов, RF 1 → 2 → 3 → 2; отдельные испытания ELR | PASS: plan, новый тестовый топик, RF 1 → 2 → 3 → 2; ELR оставался включённым на уровне 1 |
| Arenadata Streaming / ADS 4.3.1 | **НЕ ПРОВЕРЯЛСЯ НА РЕАЛЬНОМ КЛАСТЕРЕ** | **НЕ ПРОВЕРЯЛСЯ НА РЕАЛЬНОМ КЛАСТЕРЕ**; совместимость с дистрибутивом не подтверждена |

Финальные проверки Kafka 3.x не означают повторного выполнения всей прежней
матрицы на релизном JAR. Результаты относятся к описанным изолированным сценариям,
а не ко всем конфигурациям кластеров. Сертификация вендорами и сертификация для
промышленной эксплуатации не заявляются. Совместимость с Kafka 3.x не является
рекомендацией для новых промышленных развёртываний; новый клиент не исправляет
уязвимости старых брокеров.

См. [исторические результаты совместимости](https://github.com/Hellfire-son/kafka-gitops/blob/main/docs/testing/kafka-3x-compatibility-results.md)
и [финальную техническую приёмку](https://github.com/Hellfire-son/kafka-gitops/blob/main/docs/release/v0.4.0-final-review.md).

## Установка

Используйте **Java 21** и единственный **`kafka-gitops-all.jar`**. Перед запуском
сверьте SHA-256 со значением в разделе «Артефакты»:

```bash
sha256sum kafka-gitops-all.jar
java -jar kafka-gitops-all.jar --version
java -jar kafka-gitops-all.jar --help
```

Проверка контрольной суммы в PowerShell:

```powershell
Get-FileHash .\kafka-gitops-all.jar -Algorithm SHA256
```

Версия CLI должна быть `0.4.0`. Подготовьте `desired.yaml` и приватный
`client.properties` с явно заданным `bootstrap.servers`, нужным протоколом
безопасности и параметрами аутентификации и доверия для своего кластера.
Храните учётные данные вне Git. Переменные окружения `KAFKA_*` необязательны,
если файл задаёт все необходимые свойства. Ошибка чтения или формата свойств
завершает команду без молчаливого перехода к другому источнику конфигурации.

Проверьте описание локально, затем сформируйте и изучите план:

```bash
java -jar kafka-gitops-all.jar -f desired.yaml validate
java -jar kafka-gitops-all.jar --command-config client.properties -f desired.yaml plan -o plan.json
```

Для проверки описания соединение с Kafka не требуется; для plan/apply требуется.
Перед отдельным шагом записи проверьте все операции с топиками и ACL и код
завершения команды:

```bash
java -jar kafka-gitops-all.jar --command-config client.properties apply -p plan.json
```

Только для проверенного и намеренного уменьшения RF:

```bash
java -jar kafka-gitops-all.jar --command-config client.properties apply -p plan.json --allow-replication-decrease
```

Для автоматизации, которая должна исключать RF, используйте
`plan --no-manage-replication`. Параметры отдельных команд перечислены в
`plan --help` и `apply --help`. Проверяйте результаты повторных проверок
безопасности и при применении ранее сохранённого JSON-плана.

## Безопасность

Чувствительные свойства клиента и старые/новые значения в плане маскируются.
Диагностика использует ограниченное время ожидания и категории ошибок вместо
необработанных сообщений исключений Kafka. Планы и журналы всё же могут
содержать имена ресурсов, субъектов доступа и разрешённые сведения о подключении;
проверяйте их перед передачей другим лицам.

При нехватке обязательных сведений или разрешений операции RF отклоняются.
Разрешение уменьшения, `--no-delete`, актуальные метаданные, проверки ISR/ELR
и minISR остаются независимыми условиями. Планирование не запускает применение
автоматически. Заблокированный план не заменяет существующий JSON-файл: не
применяйте старый файл как результат неудавшегося запуска планирования.

Предварительная проверка и переназначение не образуют атомарную транзакцию Kafka.
Состояние может измениться между проверкой и записью; после ошибки могут
сохраниться частичные изменения. Схема JSON v1 не закрепляет исходного лидера.
Общая политика допуска размещения и объём места для копирования не доказываются
полностью доступными метаданными Admin API. Автоматического восстановления или
отката нет. Эти проверки не заменяют оценку безопасности, ёмкости и порядка
восстановления со стороны оператора.

В реальных испытаниях независимо подтверждены целевые назначения, полный ISR,

с `--no-delete`.

проверок и проверок CLI/JNI. На Kafka 4.4.0 промежуточное состояние `RUNNING`
не удалось независимо зафиксировать при очень быстром переходе RF 3 → 2;
его завершение прошло все конечные проверки. Все включённые сочетания ОС и
процессорных архитектур для нативных библиотек не испытывались. Это результаты
[финальной проверки](https://github.com/Hellfire-son/kafka-gitops/blob/main/docs/release/v0.4.0-final-review.md),
а не заявление о новых запусках тестов при подготовке документации.

## Известные ограничения

- ADS 4.3.1 не испытывался на реальном кластере; специфичные функции, политики
  и обратные переносы исправлений дистрибутива не проверены.
- Полная матрица интеграционных испытаний SASL/TLS/Kerberos/OAuth, управляемые
  Kafka/Confluent Cloud и применение ACL проверены не полностью. Проверки загрузки
  конфигурации и модульные тесты не доказывают работу реальной аутентификации
  или авторизации.
- Непустые ELR/LastKnownELR и критическая неопределённость условий безопасности
  блокируют операции RF. Уменьшение числа разделов не поддерживается.
- Большие объёмы данных, длительные нагрузки, отказы брокеров, частичное
  переназначение и аварийное восстановление требуют дополнительных испытаний.
  Сертификация для промышленной эксплуатации и полная проверка нативных
  платформ отсутствуют.
- Предупреждения об уязвимостях инструментов Gradle зафиксированы в
  [отчёте подготовки релиза](https://github.com/Hellfire-son/kafka-gitops/blob/main/docs/release/v0.4.0-release-preparation.md)
  по результатам оценки от 2026-11-13. Затронутые компоненты Guava/Jackson из
  Gradle не входят в исполняемый JAR; эти находки не доказывают уязвимости JAR.
  Датированное сканирование не гарантирует отсутствия других CVE.
- Проверенный приватный канал сообщения об уязвимостях не документирован.
  Не публикуйте учётные данные и пригодные для эксплуатации закрытые сведения
  в открытых обсуждениях проблем.
