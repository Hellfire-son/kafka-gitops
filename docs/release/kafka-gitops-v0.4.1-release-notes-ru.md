# Kafka GitOps v0.4.1

Независимый финальный QA Round 3 завершился с результатом **PASS / RELEASE READY**.
Все четыре замечания получили статус **VERIFIED FIXED**.

## Вывод PLAN и APPLY

- Подробные блоки показывают изменения топиков и ACL, предупреждения и
  заблокированные операции. Неизменяемые топики без диагностических сообщений
  учитываются в итогах. Прежние INFO-сообщения и строки `NO_CHANGE` доступны
  с `--verbose`.
- `CREATE` показывает целевые партиции, фактор репликации и заданные
  конфигурации. `UPDATE` показывает старые и новые значения и отмечает
  удаляемые переопределения. При `DELETE` топика явно указано удаление данных.
  Для ACL указаны тип и шаблон ресурса, субъект, хост, операция и разрешение.
- Для операций с RF сохраняются упорядоченные назначения реплик, ISR, ELR,
  LastKnownELR, сведения о брокерах и причины блокировки. При неоднородном RF
  в отчёте видны фактические назначения каждой партиции.
- `SUMMARY` учитывает каждый изменяемый топик один раз и показывает создание
  и удаление ACL. Категории, исключённые через `--skip-acls` или `--skip-topics`,
  помечаются `SKIPPED`. В заблокированном плане отдельно подсчитываются
  уникальные топики с блокировками и отдельные диагностические сообщения.
  Топик с блокировкой исключается из числа неизменяемых.
- APPLY показывает результат после завершения запроса или предусмотренной
  проверки. Отдельно видны успех, частичное выполнение, блокировка, отказ,
  неизвестный исход, операции без запуска и уже достигнутые цели. При APPLY из
  сохранённого JSON указан `Unchanged topics: UNKNOWN`. Явные записи без
  изменений, если они есть в файле, подсчитываются отдельно.

## Исправления по итогам финального QA

- **QA-001.** Удаление ACL учитывает подтверждённые Kafka привязки. Повторное применение
  сохранённого плана для отсутствующей привязки даёт `NO_OP`, ноль удалений и
  код 0. Если последующее удаление завершается ошибкой, подтверждённые удаления
  остаются в сводке.
- **QA-002.** План партиций, устаревший до отправки записи, даёт `BLOCKED` и код 2.
  Отправленное изменение с неподтверждённым результатом даёт `UNKNOWN`.
  Последующие операции получают `NOT_RUN`. Если ранние изменения подтверждены,
  итог остановленного APPLY будет `APPLY_PARTIAL`.
- **QA-003.** Внешние IntegrationSpec используют независимые временные пути и нормализуют
  окончания строк для точного сравнения вывода. Тесты проверяют PLAN/APPLY,
  сохранённый JSON и наблюдаемое состояние Kafka.
- **QA-004.** Финальная верификация уменьшения RF может повторно прочитать метаданные
  в пределах прежнего дедлайна, если порядок реплик уже совпадает с целью,
  переназначение завершилось, а ISR содержит все целевые и только известные
  удаляемые реплики. Успех требует точного совпадения ISR с целью на каждой
  партиции и прохождения свежих проверок безопасности. Каждый запрос Admin API
  и ожидание ответа ограничены актуальным остатком одного монотонного дедлайна.

```text
[PLAN] [CREATE] Topic: example-topic
  Partitions: 1
  Replication factor: 1
  Config cleanup.policy: compact
[SUMMARY]
  Topics: 1 to create, 0 to update, 0 to delete
  ACLs: 0 to create, 0 to delete
  Unchanged topics: 144
  Total resource changes: 1
  Status: PLAN_BUILT
  Ready for apply: FRESH_PREFLIGHT_REQUIRED
```

```text
[APPLY] [CREATE] Topic: example-topic
  Partitions: 1
  Replication factor: 1
  Config cleanup.policy: compact
  Result: SUCCESS
[SUMMARY]
  Topics: 1 created, 0 updated, 0 deleted
  ACLs: 0 created, 0 deleted
  Unchanged topics: 144
  Successful resource changes: 1
  Failed resource changes: 0
  Status: APPLY_COMPLETED
```

## Результаты независимого QA

- 1 153 JVM-теста, 26 Python-тестов, 56 CLI-проверок и 156 проверок
  кодеков/JNI на каждой из двух ОС. Внешний IntegrationSpec на Java 21
  прошёл 76/76 на Windows и 76/76 на Linux.
- На локальных Apache Kafka 3.2.3 (ZooKeeper), 3.7.1 (KRaft), 4.4.0
  (KRaft, ELR level 1) и Confluent cp-kafka 7.9.11 (ZooKeeper, SASL/PLAIN)
  прошли Validate, read-only PLAN, создание и настройка топиков,
  увеличение числа партиций и RF 1 → 2 → 3 → 2.
- На Confluent также проверены ACL и фактический контроль доступа, пять
  циклов RF 2 → 3 → 2 и RF 4 → 6 через три rack на двух топиках. Сохранены
  порядок исходных реплик, две реплики на rack, полный ISR и сообщения.
- Естественный переходный ISR в live-прогонах не наблюдался. Его обработка
  и отклонение ответа на дедлайне подтверждены детерминированными пробами.
  ADS, Kerberos, TLS и OAuth не входили в матрицу live-проверок.

## Совместимость и безопасность

Флаги CLI, коды завершения и схема исполняемого JSON совместимы с v0.4.0.
`--include-unchanged` управляет экспортом JSON. `plan` читает состояние Kafka.
`apply` сохраняет проверки безопасности RF и брокеров, свежий preflight,
проверку завершения переназначения и прежние правила удаления и изменения RF.
Чувствительные значения в диагностике маскируются. При блокировке плана
существующий файл JSON сохраняется.

Универсальный JAR собирается с Java 21, Kafka Client 4.4.0,
Gradle 9.9.1 и Shadow 9.6.1. Версии зависимостей и лицензионные уведомления
сохранены.
