## Рекомендации для отдельного этапа публикации

Следующие действия **не выполнялись**. Они предназначены для владельца после
принятия warnings и отдельного разрешения на коммит/тег/push/Release.

1. Зафиксировать собственный HTTPS URL и проверить настройки GitHub до первого
   push. Отключить Pages и publishing automation; оставить только reviewed CI.
   Назначить private security channel. Не выбирать существующие upstream remotes.
2. Ещё раз сверить status, manifest, diff/check и два SHA-256 выше. При изменении
   кода, legal inputs, notes или сборочных параметров повторить нужные проверки:
   этот отчёт привязан к конкретному JAR, а не к любому будущему build.
3. На `feature/ads-gitops` убедиться, что index пуст. Создать временный NUL-delimited
   pathspec из строк manifest с префиксом `A `, `M ` или `D `, убрав первые два
   символа; записать UTF-8 без BOM. Выполнить явное staging только этих путей:

   ```powershell
   git diff --cached --quiet
   if ($LASTEXITCODE -ne 0) { throw 'Index is not empty; review it first' }
   $releasePaths = @(Get-Content docs/release/v0.4.0-release-files.txt -Encoding UTF8 |
       Where-Object { $_ -cmatch '^[AMD] ' } | ForEach-Object { $_.Substring(2) })
   if ($releasePaths.Count -ne 268) { throw 'Manifest changed; review it first' }
   $pathspecFile = [IO.Path]::GetTempFileName()
   $pathspecBytes = [Text.UTF8Encoding]::new($false).GetBytes(
       ($releasePaths -join [char]0) + [char]0)
   [IO.File]::WriteAllBytes($pathspecFile, $pathspecBytes)
   git --literal-pathspecs add -A --pathspec-from-file=$pathspecFile --pathspec-file-nul
   git diff --cached --check
   git diff --cached --name-status
   git diff --cached --stat
   git commit -m 'Prepare Kafka GitOps v0.4.0 release'
   $releaseCommit = git rev-parse HEAD
   ```

   До commit сравнить staged paths/status с manifest; при несовпадении остановиться.
   Не использовать blanket `git add .` или `git add -f`.
4. Убедиться, что `main` — ancestor принятого коммита. Перевести её только
   fast-forward; создать новый annotated tag без force и проверить оба commit IDs:

   ```powershell
   git merge-base --is-ancestor main $releaseCommit
   # Продолжать только при exit 0:
   git switch main
   git merge --ff-only $releaseCommit
   git tag -a v0.4.0 $releaseCommit -m 'Kafka GitOps v0.4.0'
   git rev-parse main
   git rev-parse 'v0.4.0^{commit}'
   ```

5. Отправлять только два явных refspec в проверенный собственный URL. Сначала
   dry-run; после его review — отдельный реальный push. `push.followTags=false`
   исключает неявную отправку исторических annotated tags:

   ```powershell
   git -c push.followTags=false push --dry-run --atomic <OWN_FORK_HTTPS_URL> refs/heads/main:refs/heads/main refs/tags/v0.4.0:refs/tags/v0.4.0
   git -c push.followTags=false push --atomic <OWN_FORK_HTTPS_URL> refs/heads/main:refs/heads/main refs/tags/v0.4.0:refs/tags/v0.4.0
   ```

   Не использовать `--mirror`, `--all`, `--tags`, force или отправку старых tags,
   feature/experimental branches, remote-tracking refs и `refs/codex/**`.
6. После проверки remote main/tag вручную подготовить GitHub Release на уже
   существующем `v0.4.0`, с reviewed notes и дополнением из этого отчёта. Прикрепить
   только проверенные universal JAR и versioned ZIP, опубликовать их SHA-256.
   Проверить скачанные assets по этим hashes. GHCR и Pages не публиковать.
