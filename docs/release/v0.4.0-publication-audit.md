### Исключения и `gradle.properties`

`gradle.properties` не находится в индексе и не обнаружен в истории коммитов
всех refs командой `git log --all -- gradle.properties`.
Однако он **есть в одном служебном tree-снимке `refs/codex/**`**:
blob `67691869e6f96b4e24db4d766001ef87d04721c0`.
Содержимое совпадает с текущим локальным файлом; имеется только настройка
`org.gradle.java.installations.auto-download`, без credential-параметров.
Её значение здесь не воспроизводится.

Файл исключён правилом `.git/info/exclude:9:/gradle.properties`.
Это локальное правило не переносится в новый clone/fork. В `.gitignore` имеются
`.idea/`, `*.iml`, `.gradle/`, `build/`, `out/`, `docker/data/`, `state.yaml`,
`plan.json`, `test.py`; исключения `/bin/` и `/.vscode/` тоже только локальные.
**B05:** перед публикацией внести переносимое исключение приватного properties-файла,
проверить staging и состав разрешённых refs. Сейчас файл не добавлялся в индекс.
Ignore не препятствует `git add -f` и не очищает уже существующие Git-объекты.

### Что публиковать на последующем этапе

После устранения блокеров достаточно одной публичной основной ветки с финальным,
проверенным содержимым и нового аннотированного тега `v0.4.0` на принятом коммите.
Нынешняя локальная `main` содержит только upstream 0.3.1 и не представляет новый
релиз. `feature/ads-gitops` можно сохранить как рабочую ветку, но публиковать её
для функционирования релиза не обязательно. Старые теги можно сохранить как
исторические upstream tags после проверки; массовая отправка тегов не требуется.

Использовать собственный fork remote, явно выбирать ветку/тег. Не отправлять
`refs/codex/**`, чужие экспериментальные branches и remote-tracking refs;
не использовать зеркальную публикацию `--mirror` или массовую отправку refs.
Существующие remotes принадлежат upstream, собственного remote пока нет.
Это рекомендации; никаких Git/GitHub операций публикации здесь не выполнялось.

### B02: бинарная лицензионная комплектация не готова

В fat JAR имеется **10** ресурсов с license/notice именами, включая четыре
отдельных лицензии Jackson: `FastDoubleParser-LICENSE`,
`FastDoubleParser-ThirdParty-LICENSE`, `jsoniter-scala-LICENSE`, `xjb-LICENSE`.
Все четыре сохранены побайтно. Но общие имена `META-INF/NOTICE` и
`META-INF/LICENSE.txt` обрабатываются с `DuplicatesStrategy.EXCLUDE`
(`build.gradle:143`), поэтому содержимое зависит от первого включённого файла.

| Проверка JAR | Факт | Что требуется перед распространением |
|---|---|---|
| `META-INF/NOTICE` | Сохранён YAML-вариант, 681 байт; исходные Core 2063, Databind 732 и Annotations 738 байт целиком не сохранены | Собрать применимые notices всех компонентов; часть общего текста совпадает, но это не основание терять отличающиеся credits |
| Jackson Core NOTICE | Разделы FastDoubleParser/jsoniter-scala/xjb отсутствуют в итоговом NOTICE, хотя отдельные license files сохранены | Сохранить применимые ссылки и attribution вместе с текстами лицензий |
| SLF4J `META-INF/LICENSE.txt` | Исходный MIT-текст 1159 байт не найден среди итоговых license/notice ресурсов; по этому пути находится Apache-текст другого компонента | Включить MIT-текст и copyright SLF4J отдельно |
| Logback | В исходных runtime JAR и итоговых legal resources нет отдельного EPL/LGPL-текста | Добавить выбранную лицензию, copyright и source-availability statement |
| Kafka GitOps | Корневой `LICENSE` JAR взят из Kafka; copyright Shawn Seymour в legal resources JAR отсутствует | Включить исходный LICENSE проекта под собственным именем и сохранить авторство |
| JNI-компоненты | POM лицензий недостаточно; отдельного комплекта native notices нет | Собрать notices и условия точных включённых JNI/native версий |
| Существующий ZIP | Единственный элемент — launcher с тем же JAR; отдельного legal bundle нет | Обеспечить комплектность и ZIP, и универсального JAR |

На следующем этапе подготовить component-specific `META-INF/licenses/…`
или эквивалентный комплект, общий third-party attribution/NOTICE и проверку
сохранности текстов. Простое переименование корневого LICENSE эту проблему
не решает. Пересборка после упаковочных изменений создаст другой SHA-256:
потребуются новая проверка артефакта и соответствующее обновление evidence.
В данном аудите JAR и LICENSE не исправлялись.

Build/test dependencies не входят в эти 13 runtime artifacts. Gradle/plugins,
FreeBuilder, Groovy, Spock, JUnit и прочие test libraries не следует включать
в список распространяемых runtime JAR. При выпуске дополнительных SDK,
test bundles, контейнеров или build images потребуется отдельная лицензионная
проверка их состава, включая Gradle/JRE/OS. Она сейчас не завершена.

## 7. GitHub Actions и побочные публикации

| Workflow | Триггеры | Permissions / secrets | Фактические последствия |
|---|---|---|---|
| `gradle.yml` / Java CI | Push любой branch; tags игнорируются | Для build нет явных permissions, применится repository default; `GITHUB_TOKEN`, `SONAR_TOKEN`. Отдельный dependency-submission job: `contents: write` | Docker Compose; `./gradlew --info --scan build jacocoTestReport sonar`; загрузка reports/JAR; submission dependency graph |
| `dependency-review.yml` | `pull_request` | `contents: read`; literal secrets нет | Dependency review; полноценные build/test на PR этим workflow не выполняются |
| `release.yml` | Push `main` **или любого tag** | `contents: write`, `packages: write`; GitHub token для releases и GHCR | `buildRelease`; на tag — draft GitHub release и ZIP asset; затем build/push multiarch container в GHCR, в том числе на обычный push main |
| `static.yml` | Push `main`, `workflow_dispatch` | `contents: read`, `pages: write`, `id-token: write` | Загрузка всего `./docs/` и deployment GitHub Pages |

Workflow на событие `release` отсутствует. Создание GitHub Release само по себе
не является отдельным объявленным триггером этих файлов. `draft: true` относится
только к GitHub Release и **не** блокирует последующий container push.

**B03: первый push в `main` может неожиданно начать release/container/Pages
automation**, если workflows включены и GitHub settings/permissions позволяют.
Push только `feature/ads-gitops` соответствует Java CI, но не release/Pages;
при этом CI содержит `--scan`, внешние Sonar/dependency submissions и uploads.
Сбой раннего шага может остановить последующие шаги, однако рассчитывать на
случайный сбой как на запрет публикации нельзя.

До первого push на этапе публикации нужно подготовить безопасные triggers,
минимальные permissions и явные gates для внешних публикаций либо предварительно
отключить workflows в новом repository. Реальное состояние Actions, Pages,
environments, secrets и branch protections в будущем fork здесь не проверялось.
GitHub описывает [отключение workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)
как отдельную настройку; в этом задании настройки не менялись.

Дополнительные замечания:

- `actions/create-release@v1.1.4` и `actions/upload-release-asset@v1.0.2`
  принадлежат [архивному create-release](https://github.com/actions/create-release)
  и [архивному upload-release-asset](https://github.com/actions/upload-release-asset);
  заменить на поддерживаемый способ релиза после review.
- `gradle/gradle-build-action@v3` и `gradle/wrapper-validation-action@v3`
  уже делегируют в `gradle/actions`; перейти на документированные пути:
  [setup-gradle](https://github.com/gradle/gradle-build-action),
  [wrapper-validation](https://github.com/gradle/wrapper-validation-action).
- Actions привязаны к изменяемым version tags, а не full commit SHA.
  Ограничить permissions, закрепить проверенные SHA и пересмотреть передачу
  токенов/сохранение checkout credentials согласно
  [GitHub secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use).
- `pull_request_target`, `workflow_run` с исполнением PR artifact и явных
  PR-title/body interpolation в shell не обнаружено. Dependency review имеет
  read-only права. Это положительное наблюдение, но не проверка всей цепочки actions.
- Полный Java CI не настроен на `pull_request`. Добавлять его следует с учётом
  недоверенного кода и отсутствия publishing secrets у PR jobs.
- `docker-compose` v1, старый Docker/JRE base tag и upstream Sonar project key
  требуют отдельного пересмотра. Работоспособность CI на `ubuntu-latest`
  и безопасность контейнерного образа не проверялись. Java 21 в CI уже указана.
- `--scan` и Sonar/dependency uploads — внешняя передача build metadata;
  прежде чем включать их, определить приемлемый набор передаваемых данных
  и собственные project identifiers.
