# Stage 6 — безопасное управление replication factor

Дата фиксации: 2026-11-10. Основа: joschi/kafka-gitops 0.3.1 с исправлениями Stage 1–5,
ветка `feature/ads-gitops`. Среда: Java 21, Gradle 8.14.6, Shadow 8.3.11,
Kafka Client 3.9.2; заявленная версия брокеров ADS — Kafka 4.3.1.
Подключение к брокерам для проектирования и Stage 6B1 не выполняется.

## Границы реализации

Документ фиксирует технический проект Stage 6A и уточнения контракта Stage 6B1.
В Stage 6B1 реализованы только неизменяемые модели, JSON, структурная валидация
и unit-тесты. Автоматическая генерация RF-планов, выбор брокеров, проверка живого
кластера, разрешения и выполнение reassignment относятся к следующим подэтапам.
Идентификатор алгоритма в JSON обозначает контракт будущего планировщика;
наличие этого поля не означает, что алгоритм уже реализован.

## Почему PR #52 нельзя переносить целиком

Справочная реализация: коммит `4309147` («Synchronize topic replicas + partitions (#52)»),
сравнение с `devshawn/master`. Для RF она имеет следующие проблемы:

- `KafkaService.updateTopicReplication()` вызывает `replicas.remove(replicas.size())`:
  индекс за пределами списка, уменьшение RF завершается ошибкой.
- `Collections.shuffle()` при apply делает размещение случайным. Конкретного
  проверяемого назначения в сохранённом плане нет; повторный запуск может отличаться.
- Судить об RF всего топика по первой партиции нельзя: исходный RF бывает неоднородным.
- Не хватает проверок ISR, effective `min.insync.replicas`, здоровья брокеров,
  стоек, распределения нагрузки, изменения топологии и чужого reassignment.
- Создание AdminClient внутри операций, включая вложенное получение метаданных,
  усложняет согласованность снимка и управление ресурсами.
- Завершение `alterPartitionReassignments(...).all().get()` подтверждает обработку
  запроса, но не окончание переноса. Нужна отдельная проверка фактического результата.
- Нет полноценного восстановления после частичного выполнения, ограниченного
  ожидания и безопасного протокола повторного запуска. При обработке
  `InterruptedException` следует восстанавливать interrupt status; сырые сообщения
  внешних ошибок нельзя без проверки отправлять в журнал.
- Полный перенос `TopicDetailsPlan` изменил бы сложившийся JSON-контракт.

Поэтому используются отдельные необязательные операции в существующем `TopicPlan`,
а семантика создания топиков, конфигураций и partitionPlan Stage 5 сохраняется.

## Модели и контракт JSON версии 1

`TopicPlan.replicationPlan` отсутствует у старых планов. Поле не выводится как `null`.
Если поле указано, это обязательный объект, допустимый только в `TopicPlan.UPDATE`.
`TopicDetails`, `topicConfigPlans` и `partitionPlan` сохраняют прежнюю структуру.
`toChangesOnlyPlan()` сохраняет весь RF-снимок и проверяет его до фильтрации.

| Поле TopicReplicationPlan | Назначение |
| --- | --- |
| schemaVersion | Сейчас только целое число 1; неизвестная версия отклоняется |
| action | Только UPDATE, без новых значений общего PlanAction |
| clusterId, topicId | Канонические нерезервные Kafka UUID, URL-safe Base64, 22 символа |
| partitionCount | Снимок количества существующих партиций |
| targetReplicationFactor | Единый целевой RF, 1..32767 |
| algorithm | Только preserve-rack-load-v1; версия правил размещения |
| rackPolicy | RACK_AWARE или BROKER_ONLY; неизвестные политики отклоняются |
| expectedMinInSyncReplicas | Снимок effective min.insync.replicas для будущей проверки перед записью |
| brokerSnapshot | Типизированный список BrokerSnapshot: уникальный id и необязательный rack |
| assignments | Все PartitionReplicaAssignment: partition, ordered previousReplicas, ordered targetReplicas |

Предусловия выражены конкретными полями: идентичность кластера/топика, число партиций,
предыдущий порядок реплик, effective min ISR, допустимые broker IDs и racks.
Полных `Config`, credentials, JAAS, паролей, токенов, hostnames и произвольных
контейнеров настроек в RF-моделях нет. `requiresDecreaseApproval()` и `hasIncreases()`
вычисляются из назначений; они не сериализуются и не принимаются как JSON-разрешения.

Пример с синтетическими UUID и стойками:

```json
{
  "topicPlans": [{
    "name": "orders",
    "action": "UPDATE",
    "topicDetails": null,
    "topicConfigPlans": [],
    "replicationPlan": {
      "schemaVersion": 1,
      "action": "UPDATE",
      "clusterId": "AQIDBAUGBwgJCgsMDQ4PEA",
      "topicId": "ERITFBUWFxgZGhscHR4fIA",
      "partitionCount": 2,
      "targetReplicationFactor": 2,
      "algorithm": "preserve-rack-load-v1",
      "rackPolicy": "RACK_AWARE",
      "expectedMinInSyncReplicas": 1,
      "brokerSnapshot": [{"id": 0, "rack": "rack-a"}, {"id": 1, "rack": "rack-b"}, {"id": 2, "rack": "rack-c"}],
      "assignments": [
        {"partition": 0, "previousReplicas": [0], "targetReplicas": [0, 1]},
        {"partition": 1, "previousReplicas": [1], "targetReplicas": [1, 2]}
      ]
    }
  }],
  "aclPlans": []
}
```

UUID в примере канонические; резервные ZERO_UUID и ONE_UUID использовать нельзя.
В частности, `AAAAAAAAAAAAAAAAAAAAAQ` — резервный идентификатор, непригодный для примера топика.

## Структурные проверки Stage 6B1

- Полный набор партиций 0..partitionCount-1 без пропусков и повторов, положительный
  partitionCount, непустые списки реплик, уникальные неотрицательные broker IDs.
- Каждый broker ID назначения входит в снимок; число targetReplicas равно целевому RF;
  в снимке достаточно различных брокеров. Исходный RF проверяется отдельно для каждой
  партиции и может быть неоднородным, включая сочетание увеличений и уменьшений.
- При увеличении previousReplicas остаётся точным префиксом targetReplicas.
  При уменьшении targetReplicas — упорядоченная подпоследовательность previousReplicas.
  При равном RF списки полностью совпадают. Чистый NO-OP не является RF UPDATE.
- Проверяются версия, алгоритм, операция, Kafka topic name, UUID, min ISR > 0 и
  targetRF >= expectedMinInSyncReplicas. При наличии topicDetails его partitions
  совпадает со снимком, а явно заданный replication — с целевым RF.
- RACK_AWARE требует непустых rack labels всех брокеров; BROKER_ONLY допускает
  отсутствие racks. Метки не длиннее 255 символов и не содержат управляющих символов.
  Это проверка структуры, а не доказательство оптимального размещения по стойкам.
- partitionPlan и replicationPlan одного существующего топика несовместимы.
  RF-объект при ADD/REMOVE/NO_CHANGE отклоняется, даже при фильтрации плана.
- Строгий reader отклоняет неизвестные поля/операции, неверные типы, explicit null
  вместо RF-объекта, повторяющиеся JSON-ключи и отсутствующие обязательные поля.
  Диагностика RF не повторяет входные значения или сырые Jackson exceptions.
- Сериализаторы проверяют RF до экспорта, а PlanManager сериализует до открытия
  файла: ошибка не обрезает существующий план. Защита конфиденциальных topic configs
  Stage 1–2 остаётся обязательной, в том числе при совместном хранении с RF.

**Защитная граница apply:** `PlanValidation.validateForApply()` запрещает любой RF-план
до чтения метаданных и до любых topic writes. `ApplyManager` вызывает эту проверку
вместо общей структурной проверки. Иначе старая ветка UPDATE могла бы проигнорировать
новое поле и напечатать ложный успех. Это отказ в валидации, а не реализация RF executor.
`--skip-topics` сохраняет прежнюю семантику полного пропуска топиков.

## Разрешения и защита от потери данных — следующие подэтапы

Управление RF должно включаться явно. Предлагаемые будущие параметры:
`--manage-replication` для увеличения и уменьшения; дополнительно
`--allow-replication-decrease` для любой партиции с уменьшением RF.
`--no-delete` всегда запрещает уменьшение, даже при отдельном разрешении.
Сохранённый план не является разрешением. В Stage 6B1 эти CLI-флаги и разрешения
не реализованы: все RF-применения запрещены независимо от `--no-delete`.
Отличие YAML replication само по себе по-прежнему не запускает RF-операцию.

Перед записью необходимы свежие проверки всех операций плана: cluster ID, topic UUID
(защита от пересоздания с тем же именем), partitions, упорядоченные реплики,
effective min ISR и topology snapshot. Повторить проверки непосредственно перед
каждым пакетом. Не уменьшать min ISR автоматически; запретить сочетание RF с
одновременным изменением min ISR/throttle до появления явного безопасного протокола.

Для изменения нужны живые доступные брокеры, лидер и полный ISR исходных реплик.
Для уменьшения все оставляемые реплики должны быть в ISR, целевой RF >= min ISR.
ELR не считать ISR. Доступность, ISR, диски, cordoning/fencing и отсутствие чужого
reassignment — динамические условия, которые статический JSON доказать не может.
Kafka Client 3.9.2 не предоставляет все новые поля Kafka 4.3: необходимы проверки
API capabilities, effective `cordoned.log.dirs`, здоровья выбранных брокеров и
ограничений ADS. Не подменять неподдерживаемую проверку предположением об успехе.

Kafka Admin API не имеет атомарного compare-and-set назначения вместе с условиями.
Нужен внешний single-writer lease/операционный запрет конкурирующих изменений;
повторный preflight сокращает, но не устраняет окно гонки.

## Будущий детерминированный планировщик

1. Получить назначения **всех** партиций и effective min ISR, стабильный снимок
   допустимых брокеров/racks/здоровья/нагрузки. Упорядочить партиции и tie-break по ID.
2. При увеличении сохранить весь исходный порядок; добавлять только отсутствующие
   broker IDs. Предпочитать неиспользованные стойки, затем меньшую нагрузку,
   окончательное разрешение равенства — broker ID. Считать добавленные назначения
   при планировании следующих партиций. При недостатке брокеров завершаться ошибкой.
3. При уменьшении выбирать упорядоченное подмножество, по возможности сохраняя
   текущего живого лидера и распределение по стойкам. Не переставлять оставшиеся
   реплики и не переносить лидерство без необходимости.
4. При отсутствии всех racks возможен только явно выбранный BROKER_ONLY с предупреждением;
   при частичных rack metadata по умолчанию отказ. В RACK_AWARE учитывать максимум
   доступного разнообразия стоек без ложного требования RF <= числа стоек.
5. Не менять назначения партиций с уже целевым RF. Сохранить конкретные назначения
   в JSON; apply не должен повторно запускать алгоритм размещения.

## Будущий протокол применения и восстановления

Одна управляемая Admin-сессия, конечные RPC-таймауты и отдельный deadline всей операции.
Все preflight-проверки проходят до первой записи. Для каждой партиции различать:
исходное назначение (готова), уже точное целевое и здоровое (завершена), совместимый
текущий reassignment (наблюдать), чужой/несовместимый reassignment или drift (отказ).

`alterPartitionReassignments()` вызывается только для готовых партиций;
проверяются per-partition futures. Затем `listPartitionReassignments()` и
`describeTopics().allTopicNames()` опрашиваются до отсутствия активного переноса,
точного совпадения ordered targetReplicas, полного ISR и наличия лидера.
Подтверждение RPC не означает завершение. Таймаут клиента не отменяет работу брокеров.
Не отправлять `Optional.empty()` как автоматическую отмену и не очищать чужой throttle.

Фиксировать частичные результаты в локальном журнале по hash плана и идентификаторам,
без credentials. После сбоя перечитывать состояние, проверять preconditions и
продолжать наблюдение/работу идемпотентно. Не печатать общий успех при незавершённых
партициях; восстанавливать interrupt flag, сообщать безопасную диагностику.

RF и увеличение числа партиций выполнять отдельными планами: сначала RF при
исходном числе партиций, дождаться завершения, получить свежий partitionPlan.
API не обеспечивает общей транзакции; автоматического rollback обещать нельзя.
Создание новых топиков продолжает использовать прежние TopicDetails.

## Подэтапы и тестирование

| Подэтап | Объём |
| --- | --- |
| 6B1, текущий | Модели, JSON, структурная валидация, запрет исполнения, совместимость Stage 1–5 |
| Следующий: планирование | Отдельно согласованный ReplicaAssignmentPlanner, opt-in, safe preview |
| Следующий: выполнение | Разрешения, preflight, ReassignmentExecutor, ожидание, восстановление |

Unit-матрица 6B1: increase/decrease/mixed previous RF, ordered lists, отсутствие скрытого
rebalance, все ошибочные IDs/версии/операции/типы/null, полнота назначений, broker/rack
snapshot, min ISR, конфликт partitionPlan, round-trip, старый JSON, фильтрация,
отсутствие credentials и отказ apply до Kafka. Сохраняются все 254 unit-теста Stage 1–5
и старые JSON-эталоны. Компиляция интеграционных спецификаций разрешена, запуск запрещён.

Будущая mock/fake-матрица: детерминизм и баланс/racks, недостаток/отказ брокеров,
ISR/min ISR, capabilities/ELR/cordoning, drift/пересозданный топик, чужой reassignment,
таймаут, interrupt, частичные результаты, повторный запуск и оба вида разрешений.
Проверка с реальными брокерами возможна только отдельным разрешённым этапом.

Ограничения: статическая проверка не подтверждает права ACL, ресурсы/диски/нагрузку,
ISR или актуальность снимка, не вычисляет качество rack placement и не доказывает
совместимость конкретной сборки ADS. Метки racks считаются диагностическими метаданными;
оператор не должен помещать в них секреты. Общие риски сторонних библиотек из аудита
Stage 4 здесь не устраняются. Версии зависимостей и безопасное логирование не меняются.
